# Project Structure Rules

This project follows a fixed folder layout. Every new file MUST go in the location defined below. Do not invent new top-level folders, and do not put code in a folder whose purpose doesn't match it.

## Target layout

```
.
├── app/            # Expo Router routes ONLY (screens + _layout.tsx)
├── assets/         # Static files: images, fonts, icons, sounds, lottie
├── components/     # Legacy / Expo starter components — do not add new files
├── config/         # App-level configuration (env, constants, feature flags)
├── docs/           # Project documentation (architecture, ADRs, guides)
├── ios/            # Generated by CNG — never edit by hand, gitignored
├── modules/        # Local Expo native modules (create-expo-module --local)
├── patches/        # patch-package patches for node_modules
├── src/
│   ├── components/ # Shared, reusable UI components (app-wide)
│   ├── features/   # Feature modules (domain logic + feature UI)
│   ├── hooks/      # Shared, reusable hooks (not tied to one feature)
│   ├── lib/        # Infrastructure: API client, storage, utils, SDK wrappers
│   ├── stores/     # Global state stores
│   └── theme/      # Design tokens: colors, spacing, typography, radii
└── targets/        # Apple targets (widgets, extensions) via config plugin
```

## Root folders

### `app/` — routes only
- Every file here is a screen; `_layout.tsx` files define navigators. Use Expo Router groups (`(tabs)`, `(auth)`) and dynamic segments (`[id].tsx`) as needed.
- Route files must be **thin**: read params, compose feature screens, set screen options. No business logic, API calls, or large JSX trees.
- Put the actual screen implementation in `src/features/<feature>/screens/` and re-export/render it from the route file:
  ```tsx
  // app/(tabs)/transactions.tsx
  import { TransactionsScreen } from '@/src/features/transactions';
  export default TransactionsScreen;
  ```
- Never put components, hooks, or utils inside `app/` — Expo Router would treat them as routes.

### `assets/`
- Static binary files only, grouped by type: `assets/images/`, `assets/fonts/`, `assets/icons/`, `assets/animations/`.
- File names: `kebab-case`, with `@2x` / `@3x` suffixes for density variants.

### `components/` (root)
- Contains legacy Expo starter components. **Do not add new files here.** New shared components go in `src/components/`.
- When touching a file here, prefer moving it to `src/components/` and updating imports.

### `config/`
- Static, app-wide configuration: environment variable access (`env.ts`), app constants, feature flags, third-party keys config.
- Read `process.env.EXPO_PUBLIC_*` only in this folder; the rest of the app imports typed values from here.
- No UI and no side effects on import.

### `docs/`
- Markdown documentation only (architecture notes, ADRs, onboarding, release process). No source code.

### `ios/` (and `android/`)
- Generated by Continuous Native Generation. **Never create or edit by hand.** Configure native behavior via `app.json` / `app.config.ts` and config plugins.

### `modules/`
- Local Expo native modules, one folder per module (`modules/<module-name>/`), created with `npx create-expo-module --local`.
- JS/TS wrappers for a native module live inside that module folder, not in `src/`.

### `patches/`
- Only files generated by `patch-package` (`npx patch-package <pkg>`). Never hand-write or edit patch files. Document why each patch exists in `docs/`.

### `targets/`
- Apple targets (widgets, App Clips, extensions), one folder per target (`targets/<target-name>/`) with its own `expo-target.config.js`.

## `src/` folders

All application source code (other than routes) lives in `src/`.

### `src/features/` — feature modules
Code for a single domain (e.g. `auth`, `transactions`, `budgets`, `accounts`) lives in one folder:

```
src/features/<feature-name>/
├── screens/      # Full screen components rendered by app/ routes
├── components/   # UI used only by this feature
├── hooks/        # Hooks used only by this feature
├── api/          # API calls / queries / mutations for this feature
├── store/        # Feature-scoped state (if needed)
├── types.ts      # Feature types
├── utils.ts      # Feature-only helpers
└── index.ts      # Public API of the feature
```

- Only create the subfolders a feature actually needs.
- Other code imports a feature **only through its `index.ts`**, never from its internal files.
- Features must not import from each other's internals. If two features need the same code, move it to `src/components`, `src/hooks`, `src/lib`, or `src/stores`.
- Folder name: `kebab-case`, singular or plural consistently with the domain (`transactions`, `auth`).

### `src/components/` — shared UI
- Generic, reusable components used by 2+ features (Button, Card, Input, Screen, EmptyState...).
- Components here must be presentational: no feature-specific business logic, no direct API calls, no store access unless it's a truly global store (e.g. theme).
- Group primitives in `src/components/ui/` when useful.
- If a component is used by only one feature, it belongs in that feature's `components/` instead.

### `src/hooks/` — shared hooks
- Reusable hooks not tied to a single feature (`use-color-scheme`, `use-debounce`, `use-app-state`...).
- Feature-specific hooks go in `src/features/<feature>/hooks/`.

### `src/lib/` — infrastructure
- API client and interceptors, storage wrappers (SecureStore, AsyncStorage/MMKV), date/number/currency formatting, logging, analytics, third-party SDK setup.
- Framework-agnostic where possible; no React components here.

### `src/stores/` — global state
- App-wide state only (session, user preferences, settings). One file per store, e.g. `session-store.ts`.
- State that belongs to one feature lives in that feature's `store/`.

### `src/theme/` — design tokens
- Colors (light/dark), spacing, typography, radii, shadows, and theme helpers.
- Components must use tokens from here; do not hardcode colors, font sizes, or spacing values.

## Placement decision guide

When creating a file, pick the first match:
1. Is it a screen/route or navigator? → `app/`
2. Is it a static image/font/icon? → `assets/`
3. Is it env / static config? → `config/`
4. Is it native code? → `modules/` (native module) or `targets/` (Apple target)
5. Is it used by only one feature? → `src/features/<feature>/...`
6. Is it a reusable UI component? → `src/components/`
7. Is it a reusable hook? → `src/hooks/`
8. Is it global state? → `src/stores/`
9. Is it a design token / theme value? → `src/theme/`
10. Anything else non-UI (clients, helpers, wrappers) → `src/lib/`

If nothing fits, ask the user before creating a new folder.

## Naming & imports

- Files and folders: `kebab-case` (`transaction-list.tsx`, `use-balance.ts`). Components are exported in `PascalCase`, hooks as `useXxx`.
- Platform-specific files use suffixes: `.ios.tsx`, `.android.tsx`, `.web.tsx`.
- Use the `@/` path alias (maps to the project root, see `tsconfig.json`): `@/src/components/...`, `@/config/...`, `@/assets/...`. Avoid deep relative imports (`../../../`); relative imports are fine inside the same feature.
- No barrel files (`index.ts`) in `src/components`, `src/hooks`, or `src/lib` roots unless one already exists — features are the exception and always have `index.ts`.

## Migration of existing code

The repo was created from the Expo starter and does not fully follow this layout yet. When you touch these files, move them to the correct location and update imports:
- `constants/theme.ts` → `src/theme/`
- `hooks/*` → `src/hooks/`
- `components/*` → `src/components/`

Do not mass-move files unless the user asks for it.
